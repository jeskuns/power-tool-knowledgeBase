# 扫描版 OCR 推进计划（2026-11-10 制定，2026-11-12 更新）

本计划由 `_脚本/kb_ocr_plan.py` 自动执行：按阶段串行、断点续跑、批前内存检查、定期回流。
人只需要在中断后重跑 `--run`，不需要逐批下指令。

**2026-11-20 起全自动**：启动时自动扫描源库，把新放入的 PDF 登记进普查清单；阶段按当前剩余
动态编排（S0~S5 优先，其它目录并成「S9 自动发现」）。每轮跑完自动核对，有遗漏/新增就
继续下一轮，直到全库扫描件跑完（连续一轮零进展才停并报错）。双击 `启动OCR.bat` 仍进菜单，
按 1 开跑、按 4 看进度、按 2 停止；带参数 `启动OCR.bat 1` 可跳过菜单直接开跑。

## 三、执行方式

```powershell
# 随时查看各阶段剩余与可用内存
python _脚本/kb_ocr_plan.py --status

# 按计划一直跑（建议后台、单进程）
python -u _脚本/kb_ocr_plan.py --run

# 只跑某阶段（0=S0 体系标准，1=S1 安规核心，…）/ 小批试跑
python _脚本/kb_ocr_plan.py --run --stage 0
python _脚本/kb_ocr_plan.py --run --batch 1 --max-batches 1
```

后台启动用 `Start-Process -WindowStyle Hidden`，把 stdout 重定向到
`_脚本/data/ocr_plan.log`，全程日志带时间戳、每批记录可用内存。

**解释器必须是 Python 3.14**：
`C:\Users\Administrator\AppData\Local\Programs\Python\Python314\python.exe`，
PyMuPDF / rapidocr-onnxruntime / onnxruntime 只装在这个环境。默认 `python` 是 3.15，
用错会报 `ModuleNotFoundError: No module named 'fitz'`，随后因「本批没有新增完成项」
停止整轮计划（2026-11-12 踩过一次）。启动参数里的 `-FilePath` 要写 3.14 全路径。

### 运行节奏：上班跑、下班停

本机**下班会关机**，2026-11-10 夜间批次就是在跑到第 19 个文件时随关机结束的，
属正常现象，不是脚本或内存故障。因此：

- 不追求一次性连续跑完 62 小时，按工作日分段推进；
- 下班前**不用手动停进程、不用做任何收尾**，直接关机即可；
- 单个文件跑完才写断点，中断最多损失当前那 1 个文件；
- 次日上班重跑一次 `--run`，已完成目录自动跳过，从断点接着跑；
- `ocr_plan.log` 每轮启动会另存上一轮日志（如 `ocr_plan_1110.log`），便于回看断点。

## 四、内存管理（2026-11-12 二次收紧）

本机 8 GB，两个 IDE 常占约 3 GB，可用内存曾在 1.8 GB 左右；历史上 51 页文件
曾因内存争用拖到 36 分钟。2026-11-11 16:25 日志出现「批前 1024 MB 放行 →
开文件前掉到 433 MB 触发等待」，说明 OCR 子进程启动本身要占约 600 MB，
批前阈值必须把这段预留出来。据此收紧：

| 位置 | 措施 |
|---|---|
| `kb_ocr_plan.py` 批前 | 可用内存 < **1700 MB** 就等待，每 30 秒复查，最多等 10 分钟；仍不足则本轮停止，断点不丢 |
| `kb_ocr_plan.py` 批次 | 每批 **5 个文件**即让子进程退出，缩短单进程寿命、释放 onnxruntime 常驻内存 |
| `kb_ocr_batch.py` 文件级 | `MIN_FREE_MB=1200`、`MAX_WAIT_SEC=420`，开文件前不够就等 |
| `kb_ocr_batch.py` 页级 | 每 3 页 `gc.collect()`；pixmap / OCR 结果落盘后 `del`；可用内存 < **750 MB** 时回收+等待 4 轮，仍不足则中止本轮且**不写断点** |
| 并发 | **严格单进程**：临时页图 `_page.png` 路径固定，两个进程会互相覆盖导致识别错页 |

监控：`Get-CimInstance Win32_OperatingSystem | Select-Object FreePhysicalMemory`，
或直接看 `ocr_plan.log` 里每批的「批前可用内存」。

## 五、每批做什么

1. 按阶段顺序、阶段内按目录，调用 `kb_ocr_batch.py --only <目录> --limit 5`；
   目录内按页数升序（早出成果），单个文件跑完才写断点。
2. 每 **30 分钟**（或每阶段结束）自动回流一次：
   `kb_index.py` → `kb_std_latest.py` → `sync_kb.py`（内含 `build_readers` / `build_kb_data`）
   → `build_standalone_query.py`。
   因此总目录、分类索引、需OCR清单、查询数据、站点副本会随进度持续更新，**不必等全量跑完**。
3. **查询知识库不进常规回流**：平台每天 **16:50（下午 4:50）可更新一次**，按日刷新即可，不必每批重建；
   产物改为**一份完整查询文档 + 全文文件夹**，**不打包、不生成 zip**。
   - 刷新顺序（每日 16:50 定时任务）：`python build_standard_fulltext.py`（重建
     `查询知识库/标准全文/` 821 份整合版可读正文：格式整理 / 数据清洗 / 去重 / 离线版本核查）
     → `python build_query_kb_all.py`（四库共用生成器，重建单文件，第六节 6.0 列整合版路径）。
   - 联网核查结论与来源链接人工维护在 `查询知识库/标准全文/核查记录.md`，脚本不发网络请求。
   - 标准库产物 `查询知识库/测试标准查询知识库.md`（约 0.66 MB，索引式：内嵌 OCR 进度、
     50 条现行标准、25 张速查卡全文、2144 条编目索引）；正文按文件内路径回 `全文/`（834 篇）
     与 `全文OCR/`（随 OCR 增长）取，共约 55 MB 不内嵌。
   - 旧的 `build_defan_pack.py`（生成 `得帆知识库/` 与 zip）**已废弃，不要再跑**。
   - 计划脚本 `final_pack()` 只打印提示，不自动重建。

## 六、断点与恢复

- 断点键经 `path_key()` 归一化，源目录改名不会失效；单个文件 OCR 完才写 state，中断最多损失当前 1 个文件。
- 临时页图 `_page.png` 每页覆盖，异常退出会有残留，下次自动覆盖，可忽略。
- **中断后直接重跑 `--run`**，已完成目录自动跳过。
- 内存不足中止时脚本特意**不写断点**，重跑后会自动补上那个文件。
- 日志出现「本批没有新增完成项」时脚本主动停下避免死循环，通常是 OCR 进程被杀或内存不足；
  检查 `ocr_state.json` 与可用内存后重跑即可。

## 七、验收标准

- `python _脚本/kb_ocr_plan.py --status` 各阶段剩 0；
- `python _脚本/kb_ocr_batch.py --status` 显示 `已完成 1027 / 1027`；
- `00_索引/总目录.md` 中扫描版条目都有 `[OCR全文]` 链接，`需OCR清单.md` 只剩加密件与数字缺失类；
- 上述都确认后，才手动重建查询包并核对 `全文OCR/` 篇数与 `ocr_state.json` 一致。

## 八、明确不做

- 不绕过国家标准全文公开系统的图形验证码，不抓受版权保护的强标正文。
- OCR 正文的**数值一律不可直接引用**，只用于定位条款；判定回 PDF 原件或速查卡片。
- 140 个加密件解密、现行标准清单待补 10 条属于审批/采购，不是 OCR 能解决的。
