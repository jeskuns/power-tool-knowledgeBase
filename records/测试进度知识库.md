## 2. 数据从哪来、怎么清洗的

三份原始表都是制表符分隔的文本，**编码不一致**：2024、2025 为 UTF-16（带 BOM），2026 为 GBK。表头在第 3 行（前两行是「试验二科测试进度记录表」标题和「受理人员填写／测试人员填写／审核人员填写」三段分组），数据从第 4 行开始。

解析时做了四项修复，均已核对：

| 问题 | 现象 | 处理 |
|---|---|---|
| 报告编号单元格内换行 | 一条委托出多份报告，导出时把后半截甩成独立行（2024 年 21 行、2025 年 3 行） | 按「首列不是合法合同来源」判定为续行，把报告编号拼回主记录，并把随行的测试结果／提交日期／绩效一并归位 |
| 表尾数量合计行 | 2024 末行只有数字 1228，2025 末行 1257 | 识别为合计行剔除，并用它校验解析结果：两年均与脚本累加值完全一致 ✓ |
| 多余空列 | 2024 每行尾部多 3 个空字段 | 按 18 列截断 |
| 报告编号带引号 | 如 `"GC24052102EMCT/` | 去除引号、按 `/` 和空格拆分为独立编号 |

字段名差异：2024/2025 第 9 列叫「流程接收日期」，2026 叫「流程安排日期」，本知识库统一为 **流程日期**（含义：受理/排程当天，是周期计算的起点）。

| 指标 | 口径 | 说明 |

| **绩效(天)** | 流程提交日期 − 流程日期 | 已用全量数据反推验证：**99.7% 的记录**满足该公式（误差<0.1 天）。它是「受理到报告提交入库」的全流程时长，不是纯测试时长 |

## 11. 报告编号规则（从数据反推，供科室确认）

形态：`GC` + `YYMMDD`(6位，出报告日期) + `00`(2位流水) + `类别码` + `人员码`。
例：`GC26010402DYXZ` = 2026-01-04 第 02 号，电缆弯曲类，人员码 Z。

**2026 年起出现了第二种写法**：`GC` + `YYYYMMDD`(8位年份全写) + 2位流水 + 码，如 `GC2026010701WSY`（33 个，集中在温升和 EMC）。两种写法并存说明新系统（LIMS/QMS）改了编号规则但没全部切换，跨系统查档时两种形态都要试。

观察到的规律：**末位字母随测试人员变化**（H＝胡云海、T＝田欢、Y＝印海华、Z＝朱烽丰），前段字母随项目/样品类别变化：DYX＝电缆弯曲、WS＝温升、EM＝EMC、GN＝特性曲线。

**HT 是电缆弯曲里的一条独立支线**：365 个 HT 码编号中有 360 个的型号以 `TY-DH-` 开头（HTZ 330／HTH 24／HTY 11），而 DYX 码覆盖的是各系列整机与成品线缆。两者是同项目下的不同样品类别，不是笔误。

另外，DYXH／DYXY 两类编号里 44%—61% 的型号直接写线缆厂商名（华银、永祥、华泉、盛达等 + H07RN-F／H05RN-F 规格），DYXZ 只有 7%，说明早期按厂商来样分码、后来统一并入 DYXZ。

另有 3 份报告编号带「（修订）」尾注（如 `GC24092804WSY（修订）`、`GC24051701EMCT（修订）`），说明存在报告出完再改版的返工情形，本知识库在 JSON 的 报告编号列表 里已剥掉尾注、保留原串，修订清单见 `测试进度_2024-2026.json` 的 `summary.修订报告`。

两处对不上，需科室确认后再作为规则使用：
1. 末位 Z 在 2024 年指向**印海华**（DYXZ 313 个 + HTZ 60 个），2025 年起才指向**朱烽丰**——同一个人员码换人前后含义不同；
2. 2024 年印海华同时使用 `DYXY`(34) 和 `DYXZ`(313) 两种编号，同项目同人不同码，印证末位早期可能是「样品类别」而非人员。

### 查询.py 用法（在项目根目录的 Git Bash 里执行）

```bash
cd "C:/Users/Administrator/Documents/trae_projects/工程部数字化/工程部知识库/测试进度知识库"
```
